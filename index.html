TL;DR 01

What this is

Orgs want control over what AI agents can do through LaunchDarkly's hosted MCP. The proposal adds an origin axis to the existing permission check (isAllowed(member, action) becomes isAllowed(member, action, origin)), plus org-level controls on top. It reuses the RBAC system admins already know: same roles, same teams, same policy documents.

TL;DR 02

The shape

P0 is origin-aware permissions, delivered through the existing roles/teams policy system.

P1 is three features: an org-wide agent policy ("agents can never X"), an org-chosen default, and an org kill switch. Their exact scope comes out of two conversations that happen next:

  • Meet with the Vega team to understand what Vega actually wants from agent access control. Their integration is already live; the question is what governance they need, not whether they exist.
  • Meet with the agent platform team to agree what belongs in scope for the org controls and what stays out.

TRACK 01

What a permission is

The action registry

  • Every permission is an ActionIdentifier string constant in one registry: internal/roles/action.go (~445 consts, ~410 unique strings; e.g. createFlag, updateOn, updateRules, viewProject, createAccessToken, talkToVega).
  • The same file doubles as the UI picker catalog via actionAndDescriptionMap action.go:820-824, with an explicit warning that adding an action may require a custom role migration so existing roles don't break. Anything that changes action semantics inherits that migration duty.
  • Policies don't name actions directly; they use glob ActionSpecifiers ("*", "create*") matched at evaluation time action.go:15-23.

The policy document (statement model)

  • A role is a list of Statements: { effect, actions|notActions, resources|notResources } internal/roles/custom_role.go:178-192. Effect is allow | deny (plus internal pass) custom_role.go:16-22.
  • Wire shape for APIs: StatementPostData internal/roles/statement.go:16-22; validation requires exactly one of actions/notActions and one of resources/notResources statement.go:127-140.
  • Resources are colon-specifiers with globs and tags: proj/*:env/production:flag/*;testing-tag, rendered by the ResourceIdentifier zoo in internal/roles/resource_identifier.go (flag rendering at :1878-1886).

Two kinds of roles, and this matters for us

  • Built-in roles are not policies. reader/writer/admin/owner/status/no_access are an enum in the foundation module, and their permissions are hardcoded Go checkers: e.g. adminAccessChecker.CheckAccess returns allow for everything except owner-only actions internal/access_checker/types.go:187-192; the reader baseline is memberBaseline.allows: view actions + access-token actions + follow/unfollow, unless mustBeExplicitlyAllowed types.go:1125-1133.
  • Custom roles are policies stored in CRDB custom_roles internal/roles/internal/crdb/store.go:28-30, with BasePermissions of reader or no_access as the fallback floor. Role presets just concatenate onto the statement list at read time custom_role.go:150-154.
  • Attachment: members hold Role + CustomRoleIds internal/accounts/account.go:1145-1181; teams hold CustomRoleKeys + MemberIDs internal/teams/domain/team.go:71-86 via team_custom_roles / team_members tables.

The query itself

The entire authorization question is one struct; there is no origin, caller, or client field on it today:

type ResourceAccess struct {
    Action   ActionIdentifier   // e.g. "updateOn"
    Resource ResourceIdentifier // e.g. proj/p:env/production:flag/checkout
    Aliases  []ResourceAccess   // denormalized equivalents
} // internal/roles/resource_identifier.go:71-75

So your framing is literally accurate: today it's isAllowed(member, action, resource). The proposed change is isAllowed(member, action, resource, origin).

TRACK 02

The three laws of combination

Everything about "specificity wins" vs "any block wins" collides here, so these are worth internalizing. Gonfalon has three different conflict-resolution rules depending on which layer you're at:

LayerRuleCode
Within one role's statements First matching DENY wins. The loop short-circuits on deny. internal/access_checker/statement.go:15-44
Across a member's custom roles Any ALLOW wins. "CustomRoles are opt-in… denials must be unanimous": a deny in role A is overridden by an allow in role B, in either order. types.go:526-552
Member side vs token/OAuth side Intersection: any DENY wins. The token is a ceiling on the member, never an expansion. types.go:900-922, builders.go:230-282

Corollaries that surprise people

  • Direct custom roles replace the built-in role checker entirely (not unioned with it); team roles and permission grants are then unioned on top builders.go:142-182.
  • Permission grants are special-cased outside the member∩token intersection: they can expand what a restricted token does builders.go:230-282 (BuildRequestAuthAccessChecker unwraps the union to pull the grant checker out).
  • There is no ranked specificity between, say, an org-scoped and a project-scoped grant. Scoping is just whether the resource glob matches. "Specificity wins" as a universal rule would be new evaluator semantics, not a tweak.
  • Because cross-role is any-allow, "org denies X, member role allows X" → allowed today for free if you model the org policy as just another unioned checker. But "org allows X, member denies X" → also allowed. Symmetric specificity needs an ordered evaluator (Track 07, D3).
  • Within one rank there is no tie-breaker at all: two team roles (or two of a member's direct roles) that disagree fall back to flat any-allow. A specificity design must define an explicit same-rank rule; the doc's parked "still to decide" team-vs-team question is exactly this (D3).

The union and intersection loops, verbatim

// unionAccessChecker — member side (types.go:961-982)
for _, checker := range c {
    statement, role := checker.CheckAccess(access)
    switch statement.Effect {
    case roles.DENY:  defaultStatement = statement  // remembered, not fatal
    case roles.ALLOW: return statement, role       // any allow wins
    }
}

// intersectionAccessChecker — member ∩ token (types.go:904-923)
for _, checker := range c {
    stmt, role := checker.CheckAccess(access)
    switch stmt.Effect {
    case roles.DENY:  return stmt, role  // any deny wins, immediately
    case roles.ALLOW: finalStmt = stmt
    }
}
TRACK 03

How a request gets judged

The pipeline

  • Entry: ApiAuthMiddleware wraps every api2 route internal/api2/middleware/middleware.go:36-47.
  • Credential resolution is a chain: internal JWT (LD-Token) → OAuth2 Bearer → user credential → api-… token → session cookie fallback internal/trust/oauth2/web/middleware.go:115-131, internal/foundation/foundation.go:1776-1782.
  • Once the caller is known, the per-request checker is built in exactly one place, the insertion point for any origin logic: 
    fctx.AccessChecker = access_checker.ForRequestAuth(
    member, authConfig.teamRoles, authConfig.memberPermissionGrants,
    accessToken, oauthToken, commonOpts...,
) // internal/foundation/foundation.go:1729-1736
  • ForRequestAuth internal/access_checker/builders.go:16-64: member side = computeBaseAccessChecker (custom-roles-or-builtin ∪ grants ∪ team roles); then intersect with the token checker (personal token / frozen service-token limits via a synthetic member builders.go:36-50) or the OAuth scope ceiling (makeOAuth2AccessChecker).
  • Handlers call foundation.CheckAccess(ctx, checker, ResourceAccess{Action, Resource}) inline; there is no route-metadata registry internal/foundation/custom_role_authorization.go:189-198. Mutating routes are wrapped by EnsureAccessCheck, which fails closed if no real check ran.

What's already on the request that smells like "origin"

  • authKind (session / api-token / OAuth / private / user-credential) is computed per request foundation.go:1588-1598.
  • OAuth tokens carry client_id, scopes, and RFC 8707 audience; all readable at checker-build time, all already surfaced by caller-identity internal/api2/get_caller_identity.go:120-133.
  • There's precedent for origin-flavored checkers as wrappers: usageExceededAccessChecker and customRoleLapsedAccessChecker wrap the member's real checker and veto whole classes of actions builders.go:106-137. An "agent policy" fits this exact pattern mechanically.

Caching that will matter for a kill switch

  • api-… tokens are Redis-cached (~60s TTL) internal/access_tokens/redis/finder.go; the MCP's caller-identity results are cached 1 minute on the MCP side (per the plan doc). Any org switch has that much propagation lag unless explicitly busted.

The net has holes, and reads have no net

  • EnsureAccessCheck only guards unsafe methods: GET, HEAD, and REPORT are excluded by isUnsafeMethod, so read routes carry no enforcement net at all access_checker_required.go:151-159, 242-243.
  • Its knownOffenders list includes Api2PatchGlobalFlagByKey and Api2PatchSegmentByKey: flag and segment PATCH handlers that are heavily authorized yet each have at least one reachable <400 path with no access check, under internal security triage access_checker_required.go:194-198.
  • Consequence: an org promise like "agents can never change production flags" is only as strong as that list. Named work item: a scoped route-coverage audit before the org policy ships. The doc §4 aside ("a few screens still needing a permission-check audit") is exactly this, and it belongs in the plan as a deliverable, not an aside.
TRACK 04

What already exists for agents

Present and working

  • caller-identity: GET /api/v2/caller-identity, the endpoint the hosted MCP calls to validate a token. Returns accountId, memberId, clientId, clientName, scopes, audience, expiresAt, tokenKind, serviceToken internal/api2/get_caller_identity.go:33-51, bound unauthenticated with scanner-aware rate limiting internal/api2/api2.go:199. launchdarkly-mcp is a recognized User-Agent in rate-limit tests internal/foundation/rate_limiting/rate_limiting_test/caller_identity_scanner_limit_test.go:137-138.
  • MCP OAuth plumbing: default scopes reader writer observability offline_access internal/trust/oauth2/access/scopes.go:20-25; per-environment MCP resource URIs for audience binding internal/trust/oauth2/resource.go:18-21; DCR-registered clients are forced to public+PKCE, which is the "this is an MCP client" marker today internal/trust/oauth2/web/dcr_handler.go:223-232, internal/trust/oauth2/client_test.go:17-20 ("DCR public client with PKCE is MCP").
  • Agent client registry: a closed set of first-party agent OAuth clients (ld-factory-agent, ld-vega-agent) with IsAgentClientID driving audit co-authorship ("member + agent did this") internal/trust/oauth2/agents.go:18-44. Vega's client is ensured at boot behind flag enable-vega-oauth-client-for-hosted-mcp internal/factory_tokens/internal/token_service/oauth_token.go:64-73.
  • talkToVega is already a normal action on proj/*:vega/* internal/roles/action.go:618, implicitly granted to members via the baseline types.go:1125-1133.
  • Org-switch precedent: AccountLite.IsGeneralGenAiEnabled: an account-level boolean, patched via internal API, guarded by its own action updateIsGeneralGenAiEnabled internal/accounts/account_lite.go:52-55, internal/api_internal/account_endpoints/account.go:646-654. An MCP kill switch is a clone of this pattern.

Confirmed absent (zero hits, verified)

  • No useMcp action or permission anywhere.
  • No ld-mcp-server OAuth client. MCP clients today are anonymous DCR public clients, not a named first-party client.
  • No RFC 8693 token exchange: advertised grant types are only authorization_code, refresh_token, client_credentials internal/trust/oauth2/web/well_known_handler.go:62-66. A token-exchange swap would be genuinely new.
  • No multi-secret rotation: Client holds a single SecretEncrypted internal/trust/oauth2/client.go:60-91, and DCR rejects confidential auth methods outright internal/trust/oauth2/web/dcr_handler_test.go:120-125.
  • No org-level "agent policy" model or store.

SIDE B

TRACK 05

P0: the origin axis

Goal (your words): permission members, teams, and roles through the existing policy systems: the exact same permissions, but "through the MCP," whatever harness the member connects with. isAllowed(member, action) → isAllowed(member, action, origin).

Why the instinct is good

  • The codebase already half-knows origin: authKind, OAuth client_id, and audience are all present at checker-build time foundation.go:1588-1598, get_caller_identity.go:120-133. The axis formalizes what's currently scattered.
  • It dissolves special cases instead of adding them: Vega becomes origin=vega, the hosted MCP becomes origin=mcp, Terraform/scripts stay origin=direct. The closed agent-client set in agents.go:34-38 is a hand-maintained version of exactly this idea.
  • It generalizes past MCP: "contractors' tokens may never write production" and "CI may only read" are the same feature with different origin values.

The fork in the road (details + pros/cons in Track 07, D1/D4)

  • Shape A: origin as a statement condition (AWS IAM Condition analogue): statements gain an optional origin matcher, so one policy language can say allow updateOn on proj/*:env/production when origin=mcp. Maximum expressive power, maximum blast radius: the Statement struct custom_role.go:178-192, every evaluator, RoleBuilder UI, access-summary, token inline roles, and the custom-role migration system all learn a new concept. And the blast radius crosses repos: gonfalon statements are converted into the shared foundation/authorization engine for access reps (ConvertStatements, internal/access_checker/auth_builders.go:22-44), so a statement-level origin condition must land in the foundation module and every rep consumer, not just here.
  • Shape B: origin as a parallel policy layer: statements stay untouched; a separate "agent policy" document is evaluated only when the request's origin=mcp, composed as a wrapper/intersection at ForRequestAuth builders.go:16-64, the same mechanical pattern as usageExceededAccessChecker. Tiny blast radius, but two policy languages to reason about, and the "same permissions, through the MCP" dream is only approximated. A gonfalon-only wrapper also governs nothing evaluated elsewhere. Any o11y-local evaluation (observability-side enforcement) stays out of its reach.

The catch neither shape escapes

Origin is only knowable if the token says so. OAuth tokens do (client_id / audience). api-… access tokens forwarded through the MCP are indistinguishable from scripts, which is precisely the hole the proposed token exchange exists to close, and why it's a hard prerequisite for P0's promise rather than an implementation detail (see D2).

TRACK 06

P1: org policy, default, kill switch

P1a: org-wide agent policy ("no one gets X")

  • Mechanically this is a third checker composed at BuildRequestAuthAccessChecker builders.go:230-282; the only question is its combination law: hard ceiling (intersection, types.go:900-922) vs specificity-ranked (new code). That is D3, the biggest decision in the whole effort.
  • Storage can literally be the custom_roles machinery with an account-scoped marker: statements, validation, RoleBuilder UI, and the presets system all come along for free.
  • Access-summary honesty ships with it: the member/team access-summary must gain a per-origin evaluation (direct vs via-MCP), a named work item delivered with the org policy, not discovered in QA.

P1b: org-chosen default (default-on vs default-off)

  • Precedent exists inside the evaluator: the reader baseline is literally a "default allow-set": view/token/follow actions unless mustBeExplicitlyAllowed types.go:1125-1133. An org default for origin=mcp is the same idea at a different layer: when neither the org policy nor any member/team grant mentions the action, fall to the org's chosen default.
  • "Permissions don't care" is half-true: the policy language doesn't care, but the default branch is where the evaluator currently hardcodes deny (e.g. unionAccessChecker starts from a deny statement types.go:961-982). Default-on means the agent-policy checker must be able to answer pass/allow-by-default instead, a small and well-contained change.

P1c: the faucet (org kill switch for MCP traffic)

  • Clone the IsGeneralGenAiEnabled pattern: boolean on AccountLite, internal PATCH endpoint, dedicated guarding action account_lite.go:52-55, account_endpoints/account.go:646-654.
  • Two enforcement points, both cheap: (1) at caller-identity: the MCP's validation call starts failing, so fully-blocked orgs are turned away at connect; (2) per-request, as the outermost wrapper on the checker when origin=mcp (same wrapper pattern as lapsed/usage-exceeded accounts).
  • Decision: fail-open vs fail-closed when account state can't be loaded (D6), and cache-busting (60s token cache + 1m MCP-side caller-identity cache = up to ~1-2 min of "faucet drips after shutoff").

P1d: rollout shape

  • Precedent exists: the established "ships dark, flags default-off" pattern. The kill switch and org policy should launch the same way: present, inert, opt-in.
  • Neither the doc nor this report previously answered: what happens to orgs that never pick a default before enforcement day? Least-surprise answer: default-on (= today's behavior) with loud admin UI; default-off is safer but silently breaks working harness setups. Pick before P1b ships, not after.
TRACK 07

The decisions: pros & cons

D1: where does the origin axis live?

isAllowed(member, action, origin), but typed where?

A. Origin on ResourceAccess (the query struct)
PROS
  • One struct carries the whole question; every checker sees it for free
  • Statements could later match on it (Shape A) without another signature change
CONS
  • ResourceAccess is serialized/compared/cached in many places (resource_identifier.go:71-75); a new field touches every constructor
  • It's a property of the request, not the resource; a modeling smell that will confuse future readers
B. Origin as request-scoped context on the AccessChecker (Option to ForRequestAuth)
PROS
  • Single threaded insertion point: builders.go:16-64 + one Option; existing checkers untouched
  • Matches how isLapsed / isUsageExceededReadOnly already flow as Options builders.go:106-137
CONS
  • Statements can't match on origin, which caps you at Shape B (parallel policy layer)
  • Any checker that needs origin must be origin-aware explicitly
C. Origin encoded in the token itself (stamp at mint/exchange)
PROS
  • Unforgeable-ish: the credential is the proof of origin; no trusting headers or client claims
  • Works across services (observability re-checks) without each service re-deriving origin
CONS
  • Requires the planned token exchange for api-… tokens, the parked, un-built dependency
  • OAuth-side only until confidential-client + rotation work lands (zero multi-secret support today, client.go:60-91)
Likely answer: B for the evaluation axis, with C as the transport that feeds it, but the o11y path inverts that priority: the doc §4 promise ("Observability re-checks with Gonfalon per request") is a separate request carrying no MCP request context, so origin must be reconstructible from the token itself. For cross-service, C is mandatory, not optional. A only if Shape A (statement conditions) wins in D4.
D2: how do we know a request came via MCP?

Everything depends on this. Gonfalon can only apply an agent policy to traffic it can identify.

A. OAuth-only identification (client_id / audience / DCR-PKCE marker): ship P0 for OAuth, defer api-… tokens
PROS
  • Works with zero new gonfalon crypto: audience already bound to MCP resources resource.go:18-21, client_id already on the token
  • Most MCP users connect via OAuth today
CONS
  • api-… token users are a silent, uncontrolled lane through the MCP; the org switch lies to exactly the admins it's sold to
  • Two-tier enforcement is hard to explain in UI and docs
  • Every existing OAuth token is audience-less until the legacy-token revocation work lands (unstarted); "audience already bound" holds only for newly minted tokens
  • Gonfalon REST still accepts MCP-audience tokens directly today (a known open gap); "MCP audience ⇒ came via MCP" is false, so audience alone misclassifies direct API calls made with an MCP-minted token
  • Vega's hosted-MCP tokens fall back to the factory client ID per environment until EnsureVegaOAuthClient succeeds (oauth_token.go:64-73), so origin=vega silently classifies as factory
B. Token exchange first (MCP swaps every caller token for an MCP-stamped one)
PROS
  • One uniform origin signal for OAuth and api-… tokens; the policy applies to 100% of MCP traffic
  • Kills the time-boxed exception on schedule instead of letting it fossilize
CONS
  • Real prerequisites: first confidential server client (ld-mcp-server), dual-secret rotation (doesn't exist, client.go:60-64), exchange handler (doesn't exist, well_known_handler.go:62-66)
  • Swapped token must reference the original token's limits or the swap silently widens restricted tokens, a new token-lineage concept
C. Trust an MCP-signed header / caller-identity assertion without exchange
PROS
  • Cheapest path to covering api-… tokens
CONS
  • Any client can set the same header to evade the policy (or forget it to evade attribution); origin becomes spoofable by design
  • Security review will (correctly) eat this alive
B is the honest version of the feature; A buys less than it first claims: the crypto is free, but the identification stays porous until legacy-token revocation and the direct-token gap are closed, so label it loudly "OAuth connections only" if it ships. The prerequisite set is bigger than the token exchange alone: the full prerequisite chain is still untriaged, and the o11y piece (refusing MCP-audience tokens) is the cross-service half of this same problem. C should be rejected now so it stops reappearing.
D3: precedence, specificity wins vs hard ceiling

Your latest call: "specificity wins in all cases — member override beats org policy." The doc said "any block wins." The code says a third thing (Track 02). Pick the combination law for the org agent-policy.

A. Intersection (org policy is a hard ceiling, like tokens today)
PROS
  • Zero new semantics: reuse intersectionAccessChecker types.go:900-922; admins can reason "org policy ∩ role ∩ token"
  • Safest story for security-minded buyers: the org can guarantee "agents can never X"
CONS
  • Breaks your "unless a member has an overriding permission" promise; no member exemption is possible
  • "Block one contractor" (doc §1) needs a different mechanism (it would ride RBAC, not the policy)
B. Ordered specificity evaluator (member > team > org > default; most specific mention decides)
PROS
  • Exactly your stated rule; matches how AWS-ish people expect policy inheritance to work
  • Org policy, team carve-outs, and member exceptions are one coherent system
CONS
  • Brand-new evaluation semantics in the most security-critical code in the repo. Today cross-source resolution is flat any-allow (types.go:961-982, 526-552)
  • Access-summary UI must replicate the ordering or it promises access the API denies (doc §2's own warning)
  • "Specificity" needs a definition beyond source: member-role vs member's-other-role is still unordered
C. Allow-only org policy, unioned (org grants a floor; member/team grants add; nothing at org level can deny)
PROS
  • Reuses union semantics exactly as-is: any-allow-wins gives "member override" for free
  • Simple to explain: "the org can open lanes; people open more"
CONS
  • Cannot express "no one gets X", the literal headline feature of P1a. Probably disqualifying on its own.
DECIDED: Option A: the org agent-policy composes as an intersection (hard ceiling), reusing intersectionAccessChecker types.go:900-922. Member-override is rejected; "block one contractor" rides plain RBAC (role assignment), not the policy. Token limits remain a hard ceiling outside the ordering (types.go:900-922); under intersection there is no ordering for them to sit outside of, and the member∩token invariant is untouched. The parked team-vs-team tie-breaker is moot: with a hard ceiling, no same-rank specificity rule is needed.
D4: the P0 permission itself. useMcp, and on what resource?

"May use the hosted MCP at all" needs a name, a resource kind, and a place in the baseline.

A. A normal action on the account resource (e.g. useHostedMcp on "account")
PROS
  • Rides every existing system instantly: roles, teams, RoleBuilder, access-summary, token inline roles
  • Checked at caller-identity with the standard checker; per-member exempt/block is just role assignment (doc §2's "built on RBAC, not a parallel override")
CONS
  • New action ⇒ the custom-role-migration question from action.go:820-824 (existing roles with explicit statement lists won't have it; default-deny vs default-allow must be chosen, which is P1b leaking into P0)
  • Reader baseline interplay: must be added to mustBeExplicitlyAllowed handling or every reader gets/denies it silently types.go:1125-1133
B. A new resource kind (mcp) with its own tiny action set
PROS
  • Room to grow: future MCP-specific actions (per-tool grants) have a home
CONS
  • A whole resource-kind zoo entry (resource_identifier.go) for one boolean: heavy
  • Still needs the baseline + migration answers anyway
DECIDED: Option A: a normal action on the account resource. Naming still open: useHostedMcp, connectViaMcp, and useAgentAccess remain candidates. Name after the thing the member does, not the server.
D5: service tokens & the origin axis

Service tokens have no member and frozen role limits from creation time (builders.go:36-50, internal/access_tokens/access_tokens.go:115-121). What does origin=mcp mean for them?

A. Service tokens follow token policy ∩ org agent policy (no member layer)
PROS
  • Consistent with their existing semantics (creator-snapshot limits, no live member)
  • Automation via MCP stays possible but org-capped
CONS
  • "Member override" (D3-B) has no meaning for them; two rule-books again
B. Forbid service tokens via MCP entirely in v1
PROS
  • One rule-book; smallest v1
CONS
  • Breaks legitimate "agent runs my nightly automation" use cases; hard to walk back gracefully
DECIDED: Option A: service tokens follow token policy ∩ org agent policy (no member layer). The doc's §5 already half-says this ("service tokens follow the limits set when the token was created"); the org policy is an additional ceiling, never an expansion.
D6: the faucet, failure mode & propagation

When the org flips the kill switch (or when we can't tell whether it's on), what happens?

A. Fail-closed (can't load account state ⇒ deny MCP)
PROS
  • The switch means what admins think it means; incident posture
CONS
  • A gonfalon/account-store wobble takes down all customer MCP traffic; new coupling in the hot path of every MCP call
B. Fail-open with loud telemetry
PROS
  • No new availability coupling
CONS
  • During an incident is exactly when an admin reaches for the faucet; a faucet that drips when the plumbing is broken is a bad faucet
DECIDED: Option A: fail-closed (can't load account state ⇒ deny MCP). Read account state from the same cached path the request already uses (no new lookup), and document the ~1-2 min propagation from token cache (access_tokens/redis/finder.go) + MCP-side caller-identity cache. Consider an explicit cache-bust on flip.
D7: Vega, exempt, controlled, or dissolved?

Doc §7 framed exempt-vs-controlled as a binary. The origin axis offers a third answer.

C. Vega is just another origin (origin=vega)
PROS
  • The client is already identifiable (ld-vega-agent, agents.go:24) and its permission already exists (talkToVega, action.go:618)
